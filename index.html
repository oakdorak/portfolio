01Branded video production on a 16 GB laptop

Three six-second vertical ad spots and a seventeen-second reel, produced end to end on an M1 with 16 GB of memory and no cloud GPU: 1080×1920, 24 fps, graded, cross-faded, with procedurally generated music mixed to broadcast loudness.

The hard problem was never motion — it was keeping the character recognizably the same person across different framings, lighting, and locations. I solved it by constraining the model at both ends of every shot: a curated reference frame at the start, and a geometrically transformed version of that same frame at the end, letting the model fill the middle.

  • Benchmarked before committing. The fashionable model for this motion measured at 585 s per step — a projected 40–53 hours for one shot. Rejected on the measurement, not on taste.
  • Chose the pipeline by math. A distilled 4-bit alternative runs the same shot in 35–40 minutes at a fraction of the quality ceiling — the right trade for a commercial revision loop.
  • Finished in post, not in the model. Grade, sharpen, cross-fade, procedural score, and loudness normalization are deterministic steps; leaving them to the model is how generative video ends up looking generative.

02Sovereign infrastructure: a three-machine AI fleet

A self-hosted mesh across three machines running local language-model inference, a job queue, and supporting services — declared infrastructure, not a pile of shell history. I built it because the alternative is paying per token forever and handing every prompt to somebody else's server.

The representative bug: a 160 GB model set downloading at exactly zero bytes per second. Not slow — zero. Connections established, no data moving.

Symptom
0 MB/sprocesses parked in futex_wait
Root cause
IPv6 path selecttransport chose a route that moves no bytes
Fix
Resolver precedenceforced IPv4, disabled the transport
Result
0 → 1.9 MB/s160 GB verified byte-for-byte
  • Proved it wasn't the network. IPv6 to other destinations returned 200 at 16 ms; the same request to the CDN returned nothing. Narrowed to one destination before touching any config.
  • Proved it wasn't a broken route. Traceroute showed a clean path through the ISP to the CDN edge, which then went quiet on ICMP exactly as its IPv4 side does. The path was fine; the transport was picking a route that doesn't move bytes here.
  • Then found the second bug nobody would have caught. Throughput was correct but progress was not — about 89% of wall clock was being lost because the retry logic re-downloaded from the original offset on every attempt. Ninety minutes of work per gigabyte of net progress.

Tooling when the tool was the problem

Aseprite's own multi-image import corrupted animation frames non-deterministically — roughly four to five thousand pixels per frame, every single time. Rather than fight it, I reversed the binary file format and wrote a generator: custom chunk layout, zlib-compressed cel data, embedded palette, tagged animation frames. One extra byte anywhere desynchronizes the reader entirely, so the last third of the work was byte-level bisection until it loaded cleanly.

Verified at 147 of 147 frames with pixel-exact round-trip fidelity, which means an artist can open the output and edit it without silent damage.
